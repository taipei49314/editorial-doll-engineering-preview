# ADR 0011: Require owner-controlled publication directories

Status: accepted

## Context

M2.2 publishes directories and removes its own temporary files on Windows and
Linux using only Node standard-library filesystem APIs. Those APIs can inspect
path identities and reject links, but they do not expose one portable primitive
for directory-handle-relative opens, identity-conditional unlink, or an atomic
no-replace directory rename on both platforms.

Repeated path checks therefore cannot prove safety against a malicious process
running as the same operating-system account and replacing a checked pathname
in the interval before the next path-based system call. Claiming otherwise
would turn a best-effort check into a false sandbox guarantee.

## Decision

- The source root, generated root, and report parent are operator-controlled
  local or CI directories for the complete command lifetime. Their ACL and
  process isolation must prevent an untrusted same-account process from
  renaming or modifying path components concurrently.
- The publication lock serializes cooperating pipeline publishers. It is not a
  security boundary against an untrusted process that ignores or removes it.
- Within that trust boundary, every observable path boundary is checked for
  containment, stable identity, regular type, symlink, and junction/reparse
  substitution. Owned-stage cleanup deletes only entries whose recorded
  identities and exact tree are still present.
- Tests inject mutations at deterministic command phase and filesystem hook
  boundaries. They prove rejection and sentinel preservation at those
  boundaries, plus normal publisher contention; they do not claim to close a
  same-account sub-system-call race.
- A future hostile multi-tenant runner must add an approved native
  directory-handle-relative/no-replace layer or OS sandbox before reusing this
  publication protocol.

## Consequences

- The local application and isolated CI use case has a clear, testable safety
  contract without adding an unapproved native dependency.
- Pre-existing and checkpoint-injected hostile links, junctions, changed
  identities, extra files, source mutations, and conflicting cooperating
  publishers are still rejected.
- Running the CLI in a directory actively writable by untrusted code under the
  same OS account is unsupported and must not be described as safe.
